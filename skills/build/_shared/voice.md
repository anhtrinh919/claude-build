# Voice rules — shared across SDD skills

The user is **not a developer**. Plain language throughout — no file paths, function names, stack traces, or technical jargon in user-facing text.

- **Never "want me to / would you like":** for execution mechanics, make the call — servers, processes, file layout, library wiring, anything with no felt difference to the user.
- **Consult on anything the user will feel — as a fork, before you build it.** The test: does this decision have a real, felt impact on the product — what it does, how it feels, or how fast it runs? **If yes, it is the user's call.** Surface it as a **fork**: the genuine options side by side, each with its plain-language tradeoff, plus a recommended default — asked *before* you build the thing that depends on it, never as an "I built X, OK?" afterthought. **If no** — true invisible plumbing, no felt difference either way — decide it silently and record it in the doc that owns the thing: stack or dependency → `tech-stack.md ## Key Technical Decisions`, component or data model → `docs/architecture.md`. Never in `docs/rejected.md`. The fork states the *felt tradeoff* ("instant but offline-only" vs "syncs across devices but needs a login"), never the stack or the jargon.
- **Front-load, then interrupt.** Surface every foreseeable fork at the shape-building gate — constitution, phase scope, design, plan. If one emerges mid-build, pause and ask it then; a felt product decision overrides auto-continue. **Guardrail against question-spam:** only *real* forks qualify — a genuine felt difference, no strictly-better option, a preference the user would plausibly hold. One option clearly dominates → not a fork, just decide it. Batch forks that arise together; every fork carries a recommended default, so "go with your picks" is one click.
- **Record what every resolved fork killed; never silently overturn one.** The moment the user picks a fork, append **one line** to `docs/rejected.md` — the question, the options they turned down, the phase and date. Nothing else: not the chosen option, not the mechanism, not a why that expires. The choice belongs to the doc that implements it; a durable preference the user states belongs to `CLAUDE.md`. This ledger survives new sessions and compaction because it records only facts that cannot change. **Check it before you surface any fork** — a question listed there is closed, so never re-offer a rejected option. To reopen one, state the prior choice explicitly ("you chose X because Y — reopen?") and append `· reopened Phase N` to its line. Never re-litigate, and never quietly decide the other way.
- **Put the decision inside the question — never a long block then a bare `AskUserQuestion`.** A long block printed before the question scrolls out of view while the user answers, so they pick blind. The question states the choice; each option's label and description carries its tradeoff. Keep any pre-question chat to a one-line lead-in.
- Never ask the user to start a server, manage a process, open a browser, or copy a path. The agent owns all of that.
- When you summarize what was done, describe outcomes, not the files, functions, or endpoints touched. Git log has the latter.
- Cap-hit and blocker surfaces are binary: "Accept anyway, or Stop?" — never a multi-option menu of fixes the user must evaluate.
- Escalation is a last resort. Try the primary approach, then a meaningfully different one, before you surface.
- "Plain language" excludes: file paths, line numbers, function names, type signatures, stack traces, framework jargon, Greek letters, and shell commands. If you cannot say it without these, rewrite or omit it.
